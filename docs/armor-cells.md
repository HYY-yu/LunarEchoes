# 待决定的单格装甲候选

本分支对应 Issue #22 第 1 项，仍是待人类批准的重大候选。没有合并主线。用户明确每次有效受击扣一整格并隐藏原始血量数字；初始容量、升级、修复与兼容版本不是已批准参数。

候选保留玩家 raw HP 单位，核心冻结的 `ARMOR_RULES` 是唯一规则来源。初始100 HP为10格，每格10 HP；所有被接纳的接触、Boss接触和敌弹统一扣10 HP。hull上限增加20 HP即2格，立即修复最多40 HP即4格。每1800个战斗tick尝试修复10 HP，即每30模拟秒1格。60tick受击无敌、冲刺免伤与最后tick边界、敌人HP、友方武器、敌潮和180秒终局规则没有改动。

接触伤由8变10，敌弹12变10，Boss接触25变10。无升级和修复时满甲致死次数由普通接触13、敌弹9、Boss4次变为统一10次。hull的容量25变20、修复45变40。被动修复的未封顶长期平均相同，实际等待、溢出与生存体验不同，不能据此断言平衡相同。

保留原先“先修复、后碰撞”的顺序。同tick修一格再有效受击一格，最后净格数可以不变。测试单独验证此边界；普通自然受击截图避开修复边界，并未改变顺序来拍出扣格。若产品要求每个受击tick最终净格数必减1，应另决定修复优先级。

HUD每格对应真实span，满格实心、空格保留边框，按十列换行，没有假格、百分比条纹或raw HP数字。辅助信息也以格为单位，中英文hull说明直接读取共享规则。普通帧不重建格节点，只在数目、容量或语言变化时更新；显示精确除法，不用四舍五入掩盖半格。合法核心写入都保持当前与最大HP为10的整数倍，未增加可漂移的第二套格状态。

## 兼容边界

候选标签为 `lunar-armor-1`，`replay` 明确拒绝旧 `lunar-1` 和未知版本，不把旧录制重标后称为兼容。动作形状未改，没有新增存档字段、真实存储或关卡协议。`lunar-2` 保留给已决定的完整按关协议，本候选没有挪用它。该标签及不兼容选择仍待人类决定。

原 checksum26 Mac trace 保持原字节。当前90动作fixture只更新版本字段，动作不变；[候选完整trace](evidence/armor22/macos-node24.21.0.json) 由实际候选core重新捕获，CI只切换期望trace路径，不改版本检查或原verify门槛。它未触发受伤，最终c55b6ea8保持，并不证明新伤害正确或解决原跨平台终局差异。

## 容量与布局

hull没有等级上限，本候选没有添加上限。独立来源的[容量推导](evidence/armor22/capacity-bound.md) 和 [结果](evidence/armor22/capacity-bound.json) 针对合法createWorld加dispatch及现有XP/生成/终局规则，给出紧上界40格；忽略180秒终局、放宽到300秒则为48格。这是保守解析推导，不是候选自然实测或形式化证明，48作为额外防御压力，不称实际可达容量。原本机推导脚本有基线绝对路径依赖，未作为通用仓库命令复制。

`node scripts/armor-audition.mjs` 在4189提供明确标为“布局压力夹具，合成容量，非真实战斗”的正常HTTP页，只复用候选CSS和相同DOM格结构，不创建或注入gameWorld。它检查10、12、20、22、40与48个真实节点和六种既有装备布局。主游戏在4188正常运行，两者证据分开记录，压力截图不当作自然升级。
