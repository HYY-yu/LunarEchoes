# 游戏团队运行协议

本协议将六关战役拆成可验证的 Issue 与 PR。角色配置是可复用指令，不是四个常驻进程，也不包含后台唤醒器。

## 启动主协调

在本项目的 Codex chat 中发送以下任务。主协调负责队列、依赖和人类决策，具体改动交给角色 owner。

```text
使用 pstack:poteto-mode，按 docs/team-workflow.md 协调 LunarEchoes。
读取 docs/campaign-plan.md。每关 3–5 分钟，按六章顺序推进。
从第一个依赖已满足的 Issue 开始，一次先跑通一个小任务的 owner、独立验收、CI 和 PR 流程。
使用 story_director、visual_audio、balance_performance、integration_manager 角色池。
每个写入者独立 worktree 和分支，一 Issue 一个 owner，不共享写入。
低风险任务按既定验收推进；重大调整保留 PR 并建立人类决策 Issue。
先交付沙漠基地完整体验，不同时重写六关。
只在已完成、出现阻塞或需要人类决定时通知我。
```

当前会话最多四个 Agent 并发，包含主协调。四个角色按依赖轮转，不能承诺四名工人与主协调同时运行。先安排最多三个独立工作项，释放槽位后再做独立验收与集成。实际并发以运行环境限制为准。

角色文件位于 `.codex/agents/`，遵循 [Codex custom agents 格式](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)。客户端是否已加载角色需实际确认；不能仅凭文件存在声称团队已启动。模型和权限继承父会话，不在角色文件里扩大权限。

## 按 Issue 推进

1. 主协调读取当前 main、开放 PR、Issue 和验收记录，选择依赖满足的任务。
2. Issue 写明 owner、领域、允许路径、禁止事项、输入输出约定、验收命令、媒体证据与人类决定。
3. owner 创建独立 worktree、分支，采用 pstack 设计与实现流程。只有 owner 推送、rebase 或改写自己的分支。
4. owner 提交小范围 PR，并附最新 head SHA、实际验收输出与剩余限制。
5. 非作者 verifier 对当前 SHA 执行领域验收。视觉检查实际截图或动画，音频检查听感与生命周期，数值检查可复跑数据。
6. integration_manager 读取远程最新 SHA、CI 与验收，核对范围和风险。它不代替领域 verifier 阅读深层实现。
7. 满足下表才合并。合并后运行下一任务依赖的 main 验收；出现回归则建立缺陷 Issue，暂停依赖任务。

| 类型 | 必要证据 | 处理 |
|---|---|---|
| 已授权范围内的低风险改动 | 当前 SHA 的可执行验收、独立 verifier 通过、`verify` 成功、已有 required checks 全部成功 | 在既有合并授权内推进 |
| 重大调整 | 方案与影响、人类决策 Issue、当前 PR 与 SHA | 保留 PR，等待人类明确决定 |
| 检查缺失、失败或状态未知 | 失败输出、缺失项或权限错误 | 不合并，派回 owner |

这里的合并条件是团队约定。本 PR 没有配置分支保护、必需审查或自动合并；若需要平台强制执行，须另行配置并验证。不能将不存在的保护写成已启用。

人类决策至少包括重大剧情重写、核心玩法或关卡顺序变化、每关时长范围、战役解锁规则、存档与回放协议、大型依赖、性能预算放宽、收费和新增追踪。作者不能自行将这些改动降为低风险。CI 成功与用户沉默均不构成批准。批准后若方案或 SHA 改变，重新核对决定适用范围并验收。

## 四类职责

| 角色 | 拥有的结果 | 交付证据 |
|---|---|---|
| story_director | 连续六章、地图叙事、目标、对白和中英文 | 剧情连续性清单、内容检查、可跳过剧情的运行证据 |
| visual_audio | 游戏 UI、代码像素人物怪物动画、动效和合成声音 | 实机截图、动画片段、音频样本与听感记录 |
| balance_performance | 每关 180–300 秒、数值、包体和渲染性能 | 多策略种子结果、实际 gzip、明确设备的帧时间记录 |
| integration_manager | PR 增量、检查和 Issue 队列 | 最新 SHA 的检查结果、独立验收、决定记录 |

visual_audio 搜索竞品官方游戏实机画面，记录出处并原创融合，禁止 SaaS 仪表盘式界面。imagegen 用于概念与轮廓参考，评审后落实为代码像素图集。最终验收看实际游戏渲染，不能以概念图代替。外部参考素材记录出处及可用许可，不将受限素材复制进游戏。

声音至少覆盖开火、命中、击杀、受伤、拾取、冲刺、升级、Boss、胜利、失败、UI 确认与拒绝。缺项以稳定复现键建立 Issue，附当前事件路径与样本。静音、暂停、切后台和重开都须验证。

数值工作使用同种子配对比较、多种操作与升级策略，记录失败数和样本范围。目标胜率由任务定义，不能用一个全知机器人替代玩家。离线模拟不能证明浏览器 FPS。浏览器性能测试记录设备、分辨率、场景、敌人数、帧时间分布与错误，测量遵循 pstack:benchmark-checklist。

## 验收与巡检

现有统一入口是 `npm run verify`。它覆盖行为测试、代码约束、包体和输入机器人回放。游戏界面修改还须按 `.agents/skills/verify-lunar/SKILL.md` 真实试玩。新任务先补能证明目标行为的验收，再推进实现，不能用编译通过替代游戏验收。

PR、main push 和手动 workflow_dispatch 触发 GitHub Actions。工作流只读取代码，运行 Node.js 24、`npm ci` 和 `npm run verify`，不会自动合并或创建 Issue。首次 CI 成功须以 GitHub 实际 run 结果确认。

角色文件和 CI 不会自行派发工作。本次用户已选择本机定时巡检并继续工作，主协调已在 Codex app 创建并确认 ACTIVE 的每小时巡检任务，任务 ID 为 `lunarechoes`。每轮最多推进一件可验收的小任务；团队基础 PR 尚未合并时只报告未就绪，不擅自合并基础规则。

这是本机 Codex app 的外部状态，不是 Git 仓库配置。电脑需要开机、Codex app 需要运行；迁移设备或更换执行环境后，须重新创建或核对任务，并验证实际唤醒和权限。不要把此处文字当作跨设备部署已完成。工作流没有加入 cron，也没有部署 Webhook 服务、付费资源或独立常驻进程。

外部触发器配置完成后，每次巡检读取最新 main 并执行完整验收。integration_manager 用关卡、错误类别和稳定复现键查找已有 Issue，更新已有问题或创建新问题，附日志、SHA、复现与验收，并向主协调提出领域分派。通知只报告完成、失败、真实阻塞或人类决定，不重复播报无变化状态。
