## checksum 的批准边界

现状 core.ts:205–209 是对 `JSON.stringify({ ...world, events: [] })` 做 FNV-1a 风格循环；events 不是从 JSON 删除，而是保留原字段位置并替换为空数组。协议决定明确要求沿用现有 checksum 的状态取值和哈希算法，再对固定数组 `[version, stageId, rulesVersion, seed, checksum(world)]` 使用相同哈希。它没有明说新增的 World 元数据是否属于内层输入。对新增 enumerable `context` 或 `rules` 调用原样 spread 会改变内层输入；从新增 World 直接解构掉它则确实引入了一个新字段排除规则，不能将“现有代码只排除 events”与“现在还排除 context”说成字面完全相同。

推荐精确定义原 World 的旧字段集合为战斗状态，把新 context 放在其外的受控封装；内层 checksum 仍对战斗状态原样执行 `{ ...battleState, events: [] }` 和同一 hash，外层固定数组绑定 context。若 owner 采用 B 的扁平 World 以控制迁移成本，则显式剥离的仅能是新增、不可变的身份元数据；不能漏掉任何原战斗字段、改变字段顺序、把 events 删除或重新添加到末尾。应记录这是对“既有状态取值”与“上下文外层绑定”的实现解释，不宣称文档逐字规定了新字段排除。用冻结基线逐帧比较旧版 JSON 字节与新战斗投影 JSON 字节，而不只比较 32 位哈希；另测 events 不影响结果及固定数组上下文改变使终局哈希改变。如果本 Issue 明确把「World 仅排除 events」规定为新增字段也必须包含，扁平排除与该 Issue 冲突，应采用独立战斗状态封装或请人类决策，不能自行把协议改成另一种内层 hash。

## 实施门槛

先确认冻结基线可复跑；用同动作逐帧比较所有旧字段、rng、Boss 和终局，不能仅比 checksum。真实终局录制、损坏动作、旧版/未实现关卡/规则拒绝、拒绝前页面状态不变与重试新种子需分别验证。未知或不支持的规则必须在创建或替换世界前拒绝；不要让 TypeScript 字面量充当运行时验证。录制动作复制，避免外部改写。保持 FPS、玩家体验及完整沙漠切片为未验收，除非另有实际证据。
